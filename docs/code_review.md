## Top 5 Issues (ranked by severity)
1. **The Python bridge does not implement the backend contract, so the documented installation cannot reliably reach a usable `ready` state.** `scripts/start_asr_bridge.py:36-39,47,63-64,82-84,101-107` accepts `--local-files-only` but never applies it, imports the separate `mlx-qwen3-asr` package rather than the RFC's `qwen3-asr-mlx-runtime`, and reports `ready` before loading any model. The selected runtime does not install `mlx_qwen3_asr`, while the replacement library may download from Hugging Face when a path is not recognized as a valid snapshot. If that extra package is installed, the first transcription pays model-load latency under `ASRBridgeClient.swift:31-34`'s 15-second timeout, so it can time out, kill the process, and repeat the cold load. Fix: target one backend only, preferably the configured runtime's existing `qwen3-asr-mlx-jsonl-v1` bridge; make `start` load and retain the local model before returning `ready`, honor local-only mode in the actual loader, and reserve the 15-second timeout for warm transcription.
2. **Audio capture has unsynchronized cross-thread state that can race during stop or device changes.** `AudioCaptureManager.swift:4,13-18,50-52,92-103,167-176` suppresses Swift's checks with `@unchecked Sendable`, then reads `converter`, `outputFormat`, and `isRecording` from AVAudioEngine/notification callbacks while other executors mutate them. `captureQueue` protects only `pcmData`; removing a tap does not make already-running callback code safe from `converter = nil` or other lifecycle mutation. This can produce dropped final buffers, inconsistent state, or undefined behavior around stop/configuration changes. Fix: isolate all mutable capture state behind one synchronization boundary, including conversion and stop cleanup; keep lifecycle calls on one actor and serialize the render callback's converter/data access with a lock or dedicated queue rather than relying on `@unchecked Sendable`.
3. **Bridge crash recovery is disconnected from app state, and terminal restart failure is silently discarded.** `ASRBridgeClient.swift:184-191,200-213` changes only the actor's private readiness and uses `try?` for an idle-process restart, while `AppState.swift:14-17,152-153,209-210` maintains a second readiness value that receives no crash/restart notifications. After an idle crash, the menu can remain green and say "Ready" throughout backoff; if all retries fail, it can remain falsely ready until the next hotkey press. Fix: expose bridge lifecycle changes to `AppState` and derive UI readiness from that single source; transition to loading during recovery and surface `restartFailed` instead of swallowing it. Removing the duplicated readiness state is simpler and prevents drift.
4. **The app has no stable macOS application identity for Microphone and Accessibility permissions.** `Package.swift:20-37` emits a bare SwiftPM executable with an embedded plist, not a signed `.app` bundle. The resulting binary is only ad-hoc signed and has no stable designated requirement, so rebuilding or moving it can invalidate TCC grants and leave users repeatedly authorizing a command-line binary rather than the menu bar app. Fix: package the executable as a conventional `MacLocalASR.app` with the existing bundle identifier, resources, usage description, and stable development/Developer ID signature. Keep it unsandboxed for the current arbitrary model/script paths and Python subprocess; enabling App Sandbox without security-scoped bookmarks and a permitted helper would break those paths.
5. **Automatic paste can send dictated text to the wrong application and still reports success.** `TextOutputManager.swift:16-37` posts a global Command-V to whichever process owns focus when transcription finishes, which may differ from the app where recording started, and returns `true` merely because the events were created. `AppState.swift:191-195` then says "Pasted" even if focus moved, the target rejected paste, or a secure field ignored it. Fix: capture the frontmost target when recording starts and auto-paste only if that same target is still frontmost when transcription completes; otherwise leave the text on the clipboard and report the clipboard fallback. Do not treat successful `CGEvent.post` calls as proof that an application accepted the paste.
